> **For bug fixes:** the `Proposed Functional Requirements` section records the existing FR(s) the bug regresses against, copied verbatim from the SRD. No new FRs are authored. **IDs are numeric** (`FR-1`, `FR-2`, …) — the downstream leaf-skill CLIs (`plc-evidence-ingestion`, `plc-acceptance-validation`, `plc-traceability-matrix`) all validate `^(FR|NFR|AC)-\d+$`. If no SRD match is found, the row still carries a numeric ID like `FR-1`; the implicit-synthesis signal lives in the `Source` column (`implicit — no SRD match found`) and the metadata table's `SRD source used` row.
>
> The downstream PLC skills parse this brief by the same section headings as a feature brief, so the brief is a *narrow feature brief* — sparsely populated but schema-compatible.

## Disclaimer

This brief is **advisory only**. It captures the bug-fix work and links Req -> Code -> Test -> Evidence for reviewer convenience. It does NOT satisfy PLC requirements, replace formal acceptance review, or replace deterministic release validation (qualified scanners, evidence generation, policy enforcement via LaunchAPI, TAVA, nSpect, ScanSpect, SonarQube, Coverity, BlackDuck, OSRB). The fix must still go through the governed PLC release process.
